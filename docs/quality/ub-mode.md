# shadowinput 编码规范：ub-mode

从 2026-11-01 起，项目默认采用 [Uncle Bob 的 ub-mode](https://github.com/unclebob/ub-mode)，用于功能开发、修复、重构和代码审查。来源固定为 [57a8bdd2 的规则](https://github.com/unclebob/ub-mode/blob/57a8bdd28e45ed41900ace0bafa2ff76dd9ed70f/SKILL.md)。本文是面向本项目的执行说明；更新来源前先检查差异。

## 先做对功能

- 写清使用者最终能看到什么，以及如何验证。先弄清领域、数据结构和状态所有者，再实现逻辑。
- 同一业务决策只在一个地方定义。先完成能简化后续工作的基础修改，再做最小的有效改动。
- 行为变更默认先写失败测试，确认失败原因，再修改代码使其通过，最后重构。测试不现实或只是纯文案、资源调整时，说明适用的验证方法，不写没有意义的测试。
- 新需求需要时重新审视设计，分成可验证的小步交付。先减少复杂度，不把新要求不断叠加到不合适的结构上；已有清晰、局部的代码无需无故重写。
- 两次修复共享同一前提且都失败时，先写明前提，核对职责与状态的分配，再决定下一步。
- 重复或易错操作先验证一个实例，再做能够复现该结果的工具。中间状态应可回退，重复执行或中途失败后重试应收敛到同一结果。
- 用类型与领域结构表达约束，避免非法状态；术语变化时维护领域说明。外部数据在入口解析验证，核心逻辑尽量纯净，不通过忽略错误或强转掩盖类型问题。
- 优先给并发参与者独立的可变状态；必须共享时，从结构上约束唯一写入者。

## 再改善质量

- 先复现，再修根因；仅吞掉异常、绕过检查或隐藏崩溃不算解决问题。
- 完成并验证一个小单元后再进入下一单元。
- 测试从真实使用入口检查可观察的行为；空实现也能通过的测试不能作为完成证据。
- 重构前锁定行为，重构后证明行为一致。避免为了指标拆出缺少意义的函数或抽象。
- 使用 [Crapper](https://github.com/unclebob/crapper) 检查函数的复杂度与覆盖率，目标为每个函数 CRAP < 10。
- 使用 [Dryer](https://github.com/unclebob/dryer) 识别相似度 >= 0.8 的重复代码，按实际领域含义消除重复。
- 使用 [Mutator](https://github.com/unclebob/mutator) 做变异测试：补上未覆盖行为，处理存活变异，删除确认无用的死代码；等价变异需注明理由。
- 运行这些工具前核对其安装、语言支持和成本。工具未接入或不支持时，明确记录“未运行/未验证”及替代检查；普通测试通过不代表 CRAP、重复度或变异测试也通过。

## 交付与记录

- 在工作记录或提交说明中记录重要操作、原因和验证结果；交付时概述结果与限制。记录不包含凭证或私人输入内容。
- 保持当前上下文精简，长输出和过程证据放入合适的工作文件，留下可定位的摘要；不因此默认委派子代理。
- 小步、有序提交，说明为什么改、改了什么、如何验证。按已授权的工作分支推送，通过项目既有 PR 流程集成主线。
- 清理工作树前确认归属、无未提交改动且没有任务使用它。未提交工作必须保留，不能当作清理对象。
- 用户当前范围、系统/开发者约束和更具体的目录规则优先；本规范不扩大删除、发布或合并授权。
